# 1단계-4 고객 앱 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 매매상사·딜러 같은 업체 직원이 안드로이드 휴대폰 앱으로 로그인해 오더를 접수(예약 포함)하고, 자기 업체 오더의 진행·기사·사진·주유비를 실시간으로 보고, 배차 전 취소·수정, 배차 후 정해진 사유의 요금 변경, 관제 문의를 하고, 상태 변화를 푸시로 받게 한다.

**Architecture:** `apps/customer`에 기사 앱과 같은 구조의 Expo 앱(expo-router)을 만든다. 서버 규칙은 ① 서버 기반의 RLS·RPC(`orders` insert/update 정책, `customer_cancel_order`, `customer_amend_order`, `top_addresses`, `unread_counts`, 사진·영수증 저장소 정책)를 그대로 쓴다. 서버에 더하는 것은 두 가지: 카카오 REST 키를 숨기는 **Edge Function `kakao`**(주소→좌표, 길 거리)와 **고객 푸시 마이그레이션 0015**. 관제 웹의 오더 입력 검사(`apps/admin/src/lib/orders/form.ts`)는 `packages/shared`로 옮겨 두 곳이 같이 쓴다. 판단 로직은 `apps/customer/src/lib`의 순수 함수로 빼서 Vitest로 TDD 하고, 화면은 `expo start --web`을 내장 브라우저로 먼저 확인, 푸시·전화·카카오맵 열기는 사용자 폰(개발용 앱)으로 확인한다.

**Tech Stack:** 기사 앱과 같은 버전(Expo SDK 58, expo-router, TypeScript strict, supabase-js v2 + AsyncStorage, expo-notifications, expo-device, expo-constants, expo-dev-client), `react-native-webview`(우편번호 검색), Supabase Edge Functions(Deno), Expo 푸시, EAS Build, Vitest

**Spec:** `docs/superpowers/specs/2026-11-16-1단계-오더흐름-design.md` — 4장(업체 계정), 5장(상태 흐름, 고객 취소는 배차 전만, 예약), **7장 고객용 화면 전체**, 9장(요금 = 구간표 + 미션, 현금/후불), 9.1(안드로이드 먼저, APK), 10장 실패 조건("고객이 다른 업체의 오더나 주소를 볼 수 있음"). 사용자와 정한 이번 결정(2026-11-18): 카카오 키는 Edge Function에만, 주소 고르기는 무료 우편번호 검색, 기사 위치는 앱 안 지도 대신 "카카오맵에서 보기" + 마지막 위치 시각, 고객 알림은 배차·출발·도착 완료·관제 취소·관제 메시지.

## Global Constraints

- **저장소가 공개(PUBLIC)다.** 키·비밀번호·`google-services.json`은 절대 커밋하지 않는다. 앱 값은 `apps/customer/.env`(git 제외)의 `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY` 둘뿐. **카카오 REST 키는 앱에 넣지 않는다** — Supabase 비밀값(`KAKAO_REST_KEY`)으로만, 사용자가 직접 넣는다.
- 사용자가 직접 할 일(Supabase 비밀값 입력, Firebase 앱 추가, 휴대폰 설치)은 대신 하지 않고 쉬운 한국어로 안내만 한다. 외부 계정 설정 변경·서버 반영은 매번 허락.
- 화면 문구는 한국어, 서버 오류는 `errorMessage()`. 버튼 높이 48 이상, 글자 16 이상(고객은 사무실·현장 둘 다).
- 실시간 구독은 `subscribeAuthed` + 채널 이름은 `uniqueTopic(...)`로.
- 내 업체 데이터만: 서버 RLS가 지키지만 앱 쿼리에도 `company_id = 내 업체`를 붙인다(실시간 필터 포함).
- 고객은 사진을 올리지 않는다(보기만). 상태를 바꾸는 RPC는 `customer_cancel_order`, `customer_amend_order`만.
- 기사 앱(`apps/driver`)은 이번 계획에서 고치지 않는다. 같이 쓸 만한 RN 코드(supabase 클라이언트, UI kit, 시간 표시, 푸시 등록)는 **복사**한다(Ruling 후보: 공용 RN 패키지는 2단계 정리 몫).
- 커밋은 작업마다, 푸시·PR은 사용자에게 묻는다. `mycar-auto/`, `carauction-auto/`, `docs/agents/`는 건드리지 않는다. 사용자에게 주는 명령은 `&&` 없이 `npx.cmd`.

## Review Focus

1. **다른 업체 오더·주소가 보임**: 목록·상세·자주 쓰는 주소·실시간 모두 내 업체 것만 → Task 3 `listQuery` 테스트(업체 필터 포함) + 서버 기존 RLS 테스트.
2. **배차된 순간 고객이 취소·수정**: 서버가 거절(`FORBIDDEN`/`NOT_CANCELLABLE` 등) → 한국어 안내 후 오더를 다시 읽음 → Task 5 `actionsFor` 테스트(상태별 가능한 동작) + 오류 문구.
3. **카카오 길찾기 실패·키 없음**: 접수가 막히지 않고 "거리를 못 구했어요. 요금을 직접 넣어 주세요"로 요금 직접 입력 → Task 4 `fareState` 테스트.
4. **예약 시간을 지난 시각·10분 뒤 미만으로 넣음, 한국 시간 변환**: 막고 안내 → shared `validateOrderForm` 기존 테스트 + Task 4 `kstInputToIso` 테스트.
5. **배차 후 요금 변경을 사유 없이**: 사유 3개(도착지 변경·경유지 추가·미션 추가) 중 하나를 꼭 고르고 그 내용도 함께 보냄 → Task 5 `amendPayload` 테스트.
